## 3. ⚠️ 那次 B 变红：**测试床漂移**，不是产品回归

- 失败断言只有一条：`NTConverterProbe.cs` 的 `lilToon 在位检测工作正常`，
  它是**前置自诊断**（`!LilToonCompatibility.AnyLilToon` ⇒ 假设验证工程**没装** lilToon）
- 前后对照（用本项目自己的报告产物）：
  - 上一轮全绿 `run-id 20260917-065952-2002`：`✅ … → False`
  - 本轮 `run-id 20260917-074425-3259`：`AnyLilToon = True`
  - `_verify-proj/Packages/` 现在**有 `jp.lilxyzw.liltoon`**（上一轮没有）——MA 批做装置 F 时把依赖
    复制进验证工程带来的
- 根因：**`sync-verify.sh` 只管我们自己的两个包，不管第三方** ⇒ 验证工程的第三方包集会漂移
- 处置：断言语义改为"**检测结果与实际安装情况一致**"（更强：验的是**检测机制**），
  并把**测试床成分写进每份报告**，让漂移可见（commit `1cb7520`）

## 4. 推送前门禁的器械（这次才做出来，补上 0.3.11 的流程漏洞）

- `_notes/make-clean-list.mjs`：生成 staging listing，**形状照抄已发布 `docs/vpm.json`**，
  URL 指向本地 zip，zip 名由源码 `package.json` 推导
- `_notes/stage-server.mjs`：本地 HTTP 伺服 staging（vrc-get 的 `repo add` **不接受**裸路径与 `file://`）
- 两个"会造假的坑"已记在脚本注释里：
  ① 手工构造 listing 少字段 ⇒ vrc-get **拒绝加载后静默回落到线上 listing** ⇒ 门禁拿**旧版本**跑绿（实测踩到）
  ② vrc-get `repo add` 必须走 http
- 用法：`node _notes/stage-server.mjs 8799`（后台）→ `node _notes/make-clean-list.mjs` →
  `vrc-get repo add http://127.0.0.1:8799/vpm.json clean-local` → `BUILD=1 bash _notes/verify-clean-install.sh`
