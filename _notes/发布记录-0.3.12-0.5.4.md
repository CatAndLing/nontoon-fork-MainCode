## 3. 这次补上的两个洞（这是本次发布的真正价值）

### 3.1 洞一：上一次是**推完才补**干净安装门禁 ⇒ 等于没有闸

- 本次做出**推送前**可跑的器械：
  - `_notes/make-clean-list.mjs`：生成 staging listing，**形状照抄已发布 `docs/vpm.json`**，
    URL 指向本地 zip，zip 名由源码 `package.json` 推导（不硬编码）
  - `_notes/stage-server.mjs`：本地 HTTP 伺服 staging
- 过程中**踩到并记录了两个"会造假的坑"**：
  1. **手工构造 listing 少字段** ⇒ vrc-get 拒绝加载后**静默回落到线上 listing** ⇒ 门禁拿**旧版本**
     跑出绿色（实测踩到：装的是 0.5.3/0.3.11）⇒ 所以改为"照抄已发布条目的形状"
  2. vrc-get 的 `repo add` **不接受裸路径与 `file://`** ⇒ 必须走本地 HTTP
- **期望值与安装结果都写进了日志**（防"装错版本还通过"）：
  ```
  期望版本（源码唯一真源）: {"nontoon":"0.3.12","converter":"0.5.4"}
  实际安装: com.catandling.nontoon 0.3.12 / com.catandling.nontoon-converter 0.5.4
            （+ 官方仓库的 shadercore 0.1.12 / MA 1.18.7 / NDMF 1.14.8 / VRChat SDK 3.10.5）
  ```

### 3.2 洞二：**测试床漂移**让全盘门禁出现假红（差一点被当成产品回归）

- 第一次全盘：**6/7，装置 B exit 1**，失败断言只有一条：`lilToon 在位检测工作正常`
- 前后对照（用本项目自己的报告产物）：上一轮全绿 `✅ … → False`；本轮 `AnyLilToon = True`；
  `_verify-proj/Packages/` 多出 `jp.lilxyzw.liltoon`
- 根因：MA 批做装置 F 时把依赖复制进验证工程；而 **`sync-verify.sh` 只管我们自己的两个包、不管第三方**
  ⇒ 验证工程的第三方包集会漂移，**静默改变结论**
- 处置（**不是放水**）：
  - 断言语义由"必须没装 lilToon"改为 **"检测结果与实际安装情况一致"**（更强：验的是**检测机制**）
  - 把**测试床成分写进每份报告**（lilToon / MA / NDMF / AAO / VRCSDK / shadercore 是否在场），让漂移可见
