## 1. 目标

### 1.1 主目标
把工具包**注册为一个 NDMF 插件**（`[assembly: ExportsPlugin]` + `Plugin<T>`），至少提供一个 build pass，
使**现在需要事后手工修正**的事情在**构建期自动、幂等**地完成。

### 1.2 必须搬进构建期的（按这个优先级）

1. **`[NT-FIX 31]` 渲染队列兜底** —— 现在 `Editor/NTRenderQueueFix.cs` 是个**菜单命令**。
   构建期应能按 `_RenderingMode` 自动对齐 `renderQueue`（幂等，可反复跑）。
2. **`⑤ 亮度调整` / `① 光源` 的材质写入** —— 现在由编辑期组件写材质；构建期**幂等校验/重放**一次，
   避免用户后来改了材质导致"组件说的和材质里存的不一致"。
3. **`⑤ 清理旧的非 MA 残留`** —— 能自动化的在构建期做；不能的**明确报警**，不许静默。

### 1.3 明确**不做**

- 不动**转换器**（lilToon→NonToon 生成新材质，天然是编辑期动作）。
- ⛔ 不改任何**编辑期**菜单/组件行为 —— **本批是加法**：构建期自动完成，编辑期照旧。

## 2. 硬约束（违反即返工）

1. ⛔ **编辑期行为不许变**：现有菜单、组件、写入结果必须照旧可用，**已有 avatar 的构建产物不能因此改变**
   （除非那个改变正是本批要自动化的那一项，且要在交付里明确列出）。
2. ⛔ **绝不写用户的 FX 控制器 / ExpressionParameters / ExpressionsMenu**（`目标契约 §1 支柱 4`）——
   一律走 MA/NDMF 的 API。
3. ⛔ **不许改断言 / 判据让门禁变绿**；判定**必须靠测量**（退出码 / 构建产物字段直读），不接受"我看了一下"。
4. **依赖形态要查清并如实报告**：`NTModularAvatarBridge` 是否用**反射**访问 MA？
   注册 NDMF 插件需要**编译期引用** `nadena.dev.ndmf` ⇒ 说明你**怎么加的**（asmdef `references` / `versionDefines`），
   以及**缺 NDMF 时**会怎样（MA 是必需依赖 ⇒ NDMF 传递必需，但结论要写出来，不要推断了就算）。
5. **构建期 pass 必须有可失败判据**：用**装置 F**（真实 NDMF 构建）证明 pass **真的在构建时跑了**
   —— 证据是构建日志 / 构建产物字段差异；并断言产物的 `renderQueue`（或对应字段）符合预期。
   ⛔ **不许只证明"代码被执行了"**（那是 `AGENTS.md §3` 第 6 条那种"日志说对了、画面没变"）。
